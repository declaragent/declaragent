# `rpc-client` + `rpc-server`

Paired agents exchanging typed requests over the agent-rpc bus. A
concierge agent delegates PR-review work to a specialist agent; the
specialist responds with structured findings. One process in dev, two
processes over Kafka in prod — the envelope stays byte-identical.

:::info Since v1.1
Introduced in v1.1. See [Reference → Agent RPC](/reference/rpc) for
the frozen surfaces.
:::

## Scaffold

The RPC starters are fleet templates — scaffold a fleet, then add them:

```bash
declaragent init --fleet rpc-demo && cd rpc-demo
declaragent fleet add --template rpc-server
declaragent fleet add --template rpc-client
```

Canonical starters:
[`templates/rpc-client/`](https://github.com/declaragent/declaragent/tree/main/templates/rpc-client),
[`templates/rpc-server/`](https://github.com/declaragent/declaragent/tree/main/templates/rpc-server).

## Flow

```
User → concierge ──(RequestAgent)──► broker ──(request)──► pr-reviewer
                                                             │
                                                             ▼
                                                    review-pr skill
                                                             │
                                                             ▼
User ◄── concierge ◄──(response)── broker ◄──(ctx.respond)───┘
```

Every hop carries the same `correlationId`.
`declaragent events list --correlation <id>` on either daemon surfaces
the whole chain.

## Run locally — single process

Leave `KAFKA_BROKERS` unset in both `.env` files. Both agents share an
in-memory broker.

If you've scaffolded them under a `fleet.yaml`, bring the whole fleet
up in one command:

```bash
declaragent up
```

Or, for cross-process RPC within one terminal, use `fleet run` which
shares an in-memory bus:

```bash
declaragent fleet run --agent rpc-client --agent rpc-server
```

Trigger a review via the REPL (from the client side):

```
> Please review https://github.com/acme/app/pull/42
```

The concierge calls `RequestAgent`; the pr-reviewer's skill runs; the
response comes back as a Markdown summary for the user.

## Run across two processes — Kafka

Set `KAFKA_BROKERS` in both `.env` files. Swap the `kind: memory` block
in `rpc-peers.yaml` (client side) + `capabilities.yaml` (server side)
for the commented-out `kind: kafka` block.

Terminal 1 (server first):

```bash
cd rpc-server && declaragent up
```

Terminal 2:

```bash
cd rpc-client && declaragent up
```

`declaragent down` in either terminal stops that agent's sources; `ps`
shows what's currently bound; `logs -f` tails the per-agent event log.

## What's in the client

`rpc-client/agent.yaml`:

```yaml
name: concierge
model: claude-haiku-4-5
tools:
  defaults:
    - RequestAgent
```

The `delegate` skill uses `RequestAgent`:

```yaml
to: agent://pr-reviewer
capability: review-pr
payload: { prUrl: "{{prUrl}}" }
timeoutMs: 60000
# mode omitted → defaults to "sync"
```

A status-handling table tells the LLM how to react to each possible
outcome (`ok` / `timeout` / `error` / `busy` / `abandoned`).

## What's in the server

`rpc-server/capabilities.yaml` declares `review-pr` with input + output
JSON schemas:

```yaml
version: 1
agent: agent://pr-reviewer
transports:
  - kind: memory
    topics:
      requests: agents.pr-reviewer.requests
      responses: agents.pr-reviewer.responses
capabilities:
  - name: review-pr
    timeoutMs: 60000
    idempotent: true
    inputSchema: { type: object, properties: { prUrl: { type: string } }, required: [prUrl] }
    outputSchema:
      type: object
      properties:
        verdict: { enum: [approve, request-changes, comment] }
        findings: { type: array }
        summary: { type: string }
      required: [verdict, findings, summary]
```

The `review-pr` skill calls `ctx.respond` explicitly to return
structured data instead of free-form text:

```js
ctx.respond({
  ok: true,
  data: {
    verdict: "comment",
    findings: [/* … */],
    summary: "…",
  },
});
```

## Key points

- **Transport pluggability.** The envelope is broker-agnostic.
  Replacing `kind: memory` with `kind: kafka` or `kind: nats` is the
  only change needed to go cross-process under `fleet run`; the
  sqs/amqp/mqtt factories exist too but require programmatic wiring.
- **`ctx.respond` default.** Skip it and the runtime publishes
  `{ ok: true, data: { text, stopReason, usage? } }`. Good for
  REPL-first iteration; explicit calls let you return structured data.
- **Timeouts.** `timeoutMs` on the caller is authoritative. The
  receiver's work is discarded when the caller's deadline elapses.
- **Correlation threading.** `ctx.correlationId` on the concierge's
  skill flows into the request envelope's `correlationId`, and the
  response carries it back. One trace id across both daemons.

## Inspect

```bash
declaragent fleet peers --verify          # effective peer table + live inbox ping
declaragent fleet capabilities            # aggregated capabilities.yaml view
declaragent events list --correlation <cid>    # all hops for one request
```

## Deferred

- `@declaragent/plugin-github` (diff fetching) is not yet published.
  The `review-pr` skill ships a stub response until the plugin lands.
- All broker transports (kafka, nats, jetstream, sqs, amqp, mqtt,
  memory) ship inside `@declaragent/plugin-agent-rpc` itself — there
  are no separate per-transport packages. Note `fleet run`
  auto-constructs `kafka` and `nats` from `rpc-peers.yaml`; the
  sqs/amqp/mqtt/jetstream factories are wired programmatically today.
